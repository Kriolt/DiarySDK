# Устройство пакета

Документ для тех, кто правит DiarySDK или хочет понять, откуда что берётся.
Пользовательская часть — в [README](../README.md) и [справочнике](reference.md).

## Слои

```
         диарий (authedu.mosreg.ru, myschool.mosreg.ru, esia.gosuslugi.ru)
                                    ▲
 _transport ── один httpx-клиент: таймауты, повтор чтения, куки входа
     ▲
 _api / _wire ─ запросы к конкретным путям дневника и модели их ответов
     ▲
 _mapping ──── ответы дневника → публичные модели (diarysdk.models)
     ▲
 _gateway ──── DiaryGateway: «запрос + разбор» на каждый метод; реализует _port.Diary
     ▲
 client ────── Diary, Login, LoginFlow, Student: контекст ученика, дедлайн, WriteUncertain
     ▲                     ▲                       ▲
 server (FastAPI)     remote (клиент сервера)     sync (обёртки в потоке)
```

Снизу вверх:

- **`_transport`** — общий `httpx.AsyncClient`. Ограничивает параллелизм,
  ставит таймауты, один раз повторяет чтение при обрыве или 502/503/504 и не
  повторяет запись. Превращает ответы дневника в исключения, ведёт куки входа
  (каждый вход — своя «банка», общего jar нет), скрывает свои URL из журнала
  `httpx`. Секреты в записи журнала транспорта не попадают.
- **`_api`** и **`_wire`** — «что именно спросить» и «как выглядит ответ». В
  `_api` по классу на группу эндпоинтов (`web`, `mobile`, `rating`) и сырые
  запросы (`raw`); в `_wire` — pydantic-модели ответов дневника: только поля,
  которые читает `_mapping`, остальное разрешено и игнорируется. Формат не
  сошёлся (`null` вместо списка, поле другого типа) — `UpstreamFormat` с
  путями полей, без значений.
- **`_mapping`** — чистые функции «модель `_wire` → публичная модель». Здесь
  живут все решения о том, как назвать и привести поле; сети тут нет.
- **`_gateway`** — `DiaryGateway` собирает три предыдущих слоя в методы
  интерфейса `_port.Diary` (`marks`, `homework`, `esia_start`, ...). Он же
  отмечает границу записи (`write_started`), по которой клиент отличает
  `WriteUncertain` от обычной ошибки. Интерфейс `_port.Diary` — единственное,
  что знают о дневнике слои выше.
- **`_login`** — вход по паролю и через Госуслуги (шаги, капча, код).
- **`client`** — публичное ядро: `Diary` (таймауты, дедлайн вызова, кэш
  контекста ученика — один запрос к дневнику на ученика при любом числе
  параллельных вызовов), `Login`, `LoginFlow` (5 минут жизни), `Student`,
  `Parent`. Контекст ученика знает вид доступа (`student` или `parent`) и
  выбранного ребёнка; кэш — по паре (токен, ребёнок). От вида доступа зависят
  заголовки роли (`Profile-Type`) и то, что дневник родителю не даёт
  (`NotForRole` до запроса). Контекст родителя — его профиль и GUID карточки
  (claim `msh` токена) — собирается на каждый вызов `Parent`.
- **`remote`** — `RemoteDiary` и его части: тот же интерфейс, запросы идут в
  HTTP-сервис. Знает только контракт сервиса (`diarysdk.errors`, модели).
- **`sync`** — синхронные обёртки: поток с циклом событий на экземпляр,
  классы строятся по протоколам (`_protocols`), типы лежат в `sync.pyi`.
- **`server`** — FastAPI поверх ядра: край (`edge`: ключи, лимиты, журнал,
  ошибки, схема), маршруты (`routes`), реестр входов (`services`).

Общие части: `errors` (единая иерархия и таблица «код ↔ класс ↔ HTTP-статус»),
`token` (`Token`), `_clock` (время по Москве), `_periods` (периоды по
умолчанию, общие для ядра и сервера), `_protocols`.

## Границы импортов

Их проверяет `tests/test_boundaries.py`:

- ядро (всё, кроме `diarysdk.server`) не импортирует `fastapi`, `starlette`,
  `uvicorn`: `pip install diarysdk` обходится без них;
- `diarysdk.remote` не импортирует `server`, `_login`, `_api`, `_wire`;
- ядро не импортирует `diarysdk.server` (общий счётчик запросов лежит в
  `_metrics`, а не в журнале сервера);
- весь `diarysdk.server` (не только routes/services/edge) знает о дневнике
  только публичный API и приватные `_port`, `_metrics`, `_version`;
- относительных импортов в пакете нет;
- CI ставит пакет без extras в чистое окружение и проверяет
  (`scripts/check_core_only.py`), что `diarysdk`, `diarysdk.remote` и
  `diarysdk.sync` не загружают `fastapi`, `starlette`, `uvicorn`,
  `diarysdk.server`;
- ни одной сторонней библиотеки дневника, `aiohttp`, `requests` в коде нет.

## Как держится паритет ядра и удалённого клиента

Интерфейс записан один раз — протоколами в `_protocols.py` (`DiaryLike`,
`LoginLike`, `LoginFlowLike`, `StudentLike`). Тест `tests/test_parity.py`:

- сверяет сигнатуры ядра и удалённого клиента друг с другом и с протоколом
  (имена, виды и значения по умолчанию параметров);
- прогоняет одни и те же вызовы через ядро и через удалённый клиент (сервис
  в `httpx.ASGITransport`, один и тот же подставной дневник) и сравнивает
  результаты;
- гонит таблицу ошибок в обе стороны: класс → ответ сервера → класс.

Заглушка `sync.pyi` собирается из протоколов скриптом
`scripts/gen_sync_stub.py`; тест требует, чтобы она совпадала с выводом.
Контракт HTTP закреплён снимком `tests/openapi.json`
(`scripts/openapi_snapshot.py` пересобирает его), так что ломающее изменение
видно в diff.

## Золотые снимки

`tests/golden/` хранит, что шлюз отвечает на фиксированных ответах дневника
(`tests/fixtures/`) и какие запросы шлёт: метод, URL, параметры, заголовки
(без секретов) и тело. Изменение запросов или разбора видно в diff снимков.
`tests/test_wire_golden.py` прогоняет те же запросы через настоящий
`Transport` и `httpx.MockTransport` и сверяет то, что реально ушло в сеть.
Обновить эталон: `UPDATE_GOLDEN=1 pytest tests/test_golden.py`, после чего
прочитать diff.

Фикстуры в репозитории — выдуманные данные: ни настоящих ФИО, ни токенов.

## Проверка чистоты

`scripts/check_clean.py` перед публикацией проверяет содержимое и имена всех
файлов (и, с `--history`, авторов и сообщения коммитов) на то, чего в
репозитории быть не должно: домашние пути, `probe*.json`, настоящие JWT
(фальшивые имеют подпись `c2lnbmF0dXJl`), почтовые адреса и телефоны.
Дополнительные шаблоны подаются локальным файлом `--extra`. Скрипт запускается
в CI, а `tests/test_clean.py` проверяет сами правила.

## Тесты документации

`tests/test_docs.py`:

- исполняет примеры из `README.md`: каждый блок ```` ```python ````, которому
  предшествует строка `<!-- test -->`, выполняется целиком. Блок без метки —
  просто иллюстрация. Сети нет: `Diary` подменяется ядром с подставным
  дневником, `RemoteDiary` ходит в настоящее приложение через
  `httpx.ASGITransport`, синхронные классы — так же. Ключ и адрес в примерах
  (`my-api-key`, `https://diarysdk.example`) — именно те, что подставляет тест;
- проверяет, что каждое имя из `diarysdk.__all__` упомянуто в
  `docs/reference.md`;
- примеры из `examples/` импортируются в тестах без сети (`main()` под
  `if __name__ == "__main__"`).

## Сборка и выпуск

- Версия — в `diarysdk/_version.py`, `hatchling` читает её оттуда.
- Wheel содержит только пакет (с `py.typed` и `sync.pyi`); sdist — пакет,
  тесты, примеры, скрипты и публичные документы. `scripts/check_dist.py`
  проверяет состав обоих архивов.
- Образ собирается из `Dockerfile`: `pip install .[server]`, не root, чтение
  ключей из смонтированного файла, `HEALTHCHECK` по `/healthz`.
- CI (`.github/workflows/ci.yml`): `ruff check`, `ruff format --check`,
  `pytest`, `check_clean`, сборка и `twine check` на Python 3.15
  (обязательно) и 3.16 в режиме пре-релиза (не блокирует); отдельная работа
  собирает образ и ждёт здоровья контейнера. Ничего не публикуется.
